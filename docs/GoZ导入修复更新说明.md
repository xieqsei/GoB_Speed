# GoB 插件 GoZ 导入修复更新说明

| 项目 | 内容 |
|---|---|
| 更新日期 | 2026-11-02 |
| 适用插件 | GoB (GoZBrush for Blender) |
| 适配环境 | Blender 5.2.1 / Blender 5.2 LTS，ZBrush 2026 导出的 `.GoZ` |
| 涉及文件 | `gob_s_import.py`、`gob_import.py`、`gob_export.py` |
| 影响功能 | S导入、普通导入、中文对象名、导出往返 |
| 生效方式 | 重启 Blender（扩展重载一次） |

---

## 一、问题现象

S导入模型时报错：

```
S导入失败：中模体型5.GoZ: cannot reshape array of size 2155474 into shape (4575657221408603884,4)
```

同一份文件用**普通导入**可以正常进入场景，因此一开始容易误判为文件损坏。实测该文件本身完全正常。

---

## 二、根因分析

### 2.1 GoZ 二进制块布局

`.GoZ` 的文件头与数据块布局如下（本插件导出端与 ZBrush 导出端一致）：

```text
偏移 0      26 字节   文件标识 "GoZb 1.0 ZBrush GoZ Binary"
偏移 26      6 字节   0x2E × 6
偏移 32      4 字节   u32 = 1（对象标记）
偏移 36      4 字节   u32 名称块总长度（= 24 + 名称字节数）
偏移 40      8 字节   子头（u64 = 1）
偏移 48      N 字节   "GoZMesh_" + 对象名（UTF-8）

之后为若干数据块，每个块统一为：
  +0    4 字节   块标识 tag
  +4    4 字节   块总长度 u32（含 16 字节块头，即 16 + 载荷字节数）
  +8    8 字节   计数 / 标志位
  +16   M 字节   载荷
```

### 2.2 POLYPAINT 块在 ZBrush 2026 中改变了计数宽度

旧版 S导入按 **u64** 读取 `+8` 处的计数字段。而 ZBrush 2026 写出的 POLYPAINT 块，计数字段是 **u32**，其后紧跟一个恒为 `1.0` 的 `float32`：

```text
b9 88 00 00 | c0 fb 0a 00 | ec be 02 00 | 00 00 80 3f | ff ff ff 00 ...
  POLYPAINT    块总长         count=179948   float 1.0     首个像素
```

按 u64 读取时，`count(179948)` 与 `1.0f` 的位模式 `0x3F800000` 被拼成一个 64 位整数：

```
0x3F800000_0002BEEC = 4575657221408603884
```

这个数字正好落在报错信息里。随后执行 `reshape(4575657221408603884, 4)` 立刻崩溃。

### 2.3 为什么普通导入"看起来没问题"

`gob_import.py` 读到这个异常计数后，直接在 `except` 分支里放弃整个块并 `break`，因此不抛异常 —— 但**顶点色（POLYPAINT）一直没被导入**，属于静默数据丢失。

## 三、修改内容

### 3.1 `gob_s_import.py` — 块长驱动的解析器（核心修复）

**改动位置**：`GoB_OT_s_import` 的块解析循环（约 620–700 行），新增内部函数 `block_payload()`。

**改动要点**：

1. **不再信任计数域**。所有数据块（顶点、面、UV、顶点色、蒙版、多边形组、细分）统一用「块总长 − 16」反推载荷字节数与元素个数：

   ```python
   def block_payload(block_pos):
       if block_pos + 8 > total:
           return None, 0, 0
       block_len = u32_at(block_pos + 4)
       if block_len < 16 or block_pos + block_len > total:
           return None, 0, block_len      # 块头非法，交给上层终止解析
       return block_pos + 16, block_len - 16, block_len

   # 例：顶点块
   count = payload // 12
   verts = arr(start, count * 12, '<f4').reshape(count, 3)
   ```

   这样计数写成 u32、u64 甚至干脆不写，都不影响解析。

2. **未知块安全跳过**，并加了越界保护，避免读到文件尾部之外。
3. **删除已废弃的 `u64_at()` 辅助函数**（块长驱动后不再需要）。

### 3.2 `gob_s_import.py` — 网格校验时机调整（第二个崩溃点）

**改动位置**：`_make_mesh()`（225 行）与 `_make_mesh` 调用处（786–790 行）。

`me.validate()` 会删除重复面与非法面。实测 `Merged_model_20261021_140117.GoZ` 的 519073 个面里会被删掉 31 个。原实现在**写属性之前**校验，导致随后按 `.GoZ` 面序做 `foreach_set` 时长度不匹配，报 `internal error setting the array`。

修法：

- `_make_mesh(..., validate=False)`，建网格时先不校验；
- 等 UV、顶点色、蒙版、面组等**全部逐面/逐顶点属性写完之后**，再统一执行 `me.validate()`，让删面时属性数组同步被裁剪，索引始终一致。

同时补了长度对齐防御（不一致时按较小值截断，而不是抛异常）：

| 属性 | 对齐基准 |
|---|---|
| UV | loop 数 |
| 面组 / 材质索引 | 多边形数 |
| 蒙版 | 顶点数 |

以及无面网格时 `tri_mask` 未定义的隐患。

### 3.3 `gob_import.py` — UV 读取重写

**改动位置**：新增方法 `GoB_OT_import.apply_uvs()`（104 行），替换原 UV 分支（约 340 行）。

**原实现的问题**：按 `bm.faces` 顺序"连续读"UV 流。一旦有退化面被 `from_pydata` 丢弃、或 `me.validate()` 删掉重复面，网格面数就少于文件面数，读指针立即错位，之后**所有面的 UV 全部错**。这不会报错，只会让贴图悄悄变形。

**新实现**：

- UV 块整块读成 `(文件面数, 4, 2)` 的 numpy 数组，一次 `foreach_set` 写入；
- 以「面的顶点索引元组」为键，把文件面与网格面**配对**后写入，完全不依赖面序，删面/丢面只影响自身；
- 顶点序列完全相同的重复面用 list 共存，避免其中一个面拿不到 UV。

**注意坑**：UV 块头是 `tag(4) + 块长 u32(4) + 面数 u64(8)`，读载荷前必须再 `seek(8)` 跳过面数，否则整条 UV 流偏移 8 字节，表现为 UV 全乱。

### 3.4 中文对象名保留（两处导入 + 一处导出）

**问题**：两个导入器都用 `string.printable` 过滤名称，非 ASCII 字符（中文）被整段丢弃，`中模体型5` 变成 `5`。

**改动**：

| 文件 | 改动 |
|---|---|
| `gob_s_import.py` | 名称解析改用 `c.isprintable() and c != '\x00'` |
| `gob_import.py` | 同上，替换 `''.join([... if letter in string.printable])` |
| `gob_export.py` | 名称长度域 `len(obj.name) + 24` → `len(name_bytes) + 24` |

导出端这条是**隐藏的雷**：原代码按**字符数**写长度域，而名称块按 **UTF-8 字节数**写入。中文一词 3 字节，长度域会偏小，导出的 `.GoZ` 名称块错位，ZBrush 或导入端读取时直接串位。不修这条，改完导入反而会在"导出 → 回读"往返时炸。

顺带移除了两个文件中已无用的 `import string`。

### 3.5 `gob_import.py` — 多边形组写入越界保护

原版多边形组转材质/面集是按 `.GoZ` 面序索引网格面的，当面数少于面组数时会越界。已加截断保护，`Merged_model` 这类含退化面的文件不再报 `internal error setting the array`。

## 四、验证结果

测试方式：`blender.exe --background --factory-startup --python <脚本>`，把 `paths.PATH_GOZ` 指向临时目录中的 `GoZBrush/GoZ_ObjectList.txt`，不触碰 ZBrush 正在使用的真实文件。

| loop 索引比对 | 完全一致 |

| 导入器 | 内部边 UV 一致率 |
|---|---|

| 普通导入（修复后） | **98.78 %** |

也就是说：这份文件以前用普通导入，UV 一直是错的。剩余 1.2 % 为真实的 UV 缝，属正常。

## 五、使用注意

1. **必须重启 Blender**，扩展才会重新加载修改后的模块。
2. **旧的普通导入模型需要重新导入**：之前用普通导入进场景的模型 UV 是错位的，贴图会显示错乱，重新导入一次即可。
3. 两个导入器现在结果等价：几何、UV 完全一致，S导入只是更快（21 MB 文件约 0.37 s）。
4. 若 ZBrush 后续再次改变块结构，只要「块总长 = 16 + 载荷」这条规则不变，解析器仍能工作。
